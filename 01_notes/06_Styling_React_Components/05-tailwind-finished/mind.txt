🧠 1) Component Architecture
How to think about breaking an app into pieces

Mental model
Think of a React app like a company 🏢
      The App component = CEO
      Big sections = departments
      Small components = employees

Each component has:
      ONE responsibility
      Clear input (props)
      Optional internal memory (state)

Component hierarchy (example) 
_____________________________________
App
 ├─ Header
 │   ├─ Logo
 │   └─ Navigation
 ├─ Dashboard
 │   ├─ StatsCard
 │   ├─ Chart
 │   └─ RecentTasks
 │       └─ TaskItem
 └─ Footer
 _____________________________________
 Rule of thumb:
 If a file grows past ~150 lines → it’s hiding multiple components.

Good vs bad architecture
❌ Bad:
   - One giant App.jsx
   - Logic + UI + API + styles mixed
   - Copy-paste Components
✅ Good:
   - small focused components
   - reusable UI blocks
   - clear folder structure

Example structure: 
_____________________________________
src/
 ├─ components/
 │   ├─ ui/
 │   │   ├─ Button.jsx
 │   │   └─ Card.jsx
 │   └─ layout/
 │       └─ Header.jsx
 ├─ pages/
 │   ├─ Dashboard.jsx
 │   └─ Tasks.jsx
 └─ App.jsx
--------------------------------------
Architecture is about clarity, not perfection.


🔁 2) Props + State Flow
How data moves in React
This is where most beginners get lost.
The golden rule
   - Data flows DOWN. Events flow UP.

State: local memory 🧠
   State lives in the component that owns the data.

   const [tasks, setTasks] = useState([]);

State = “things that change”
When state changes → component re-renders

-------------------------------------------

Props: read-only input 📦

Props are how parents talk to children.

<TaskItem title="Learn React" />


Child:

function TaskItem({ title }) {
  return <li>{title}</li>;
}


Props:

Cannot be changed by the child

Flow only downward

Lifting state up (critical concept)

If two components need the same data, state moves up.

App (state lives here)
 ├─ TaskList (reads tasks)
 └─ TaskForm (adds tasks)


This avoids:

Duplication

Desync bugs

Chaos

Events flow up

Child triggers change via function props:

<TaskForm onAddTask={addTask} />


Child:

props.onAddTask("New Task");


Think:

“I don’t change data. I ask my parent to.”

🎨 3) Layout Systems with Tailwind
How UI structure actually works

Tailwind doesn’t replace CSS knowledge — it forces you to understand layout properly.

The 3 layout pillars
1️⃣ Box model

Everything is a box.

Tailwind:

p-4 m-2 w-64 h-32

2️⃣ Flexbox (most common)

Use for:

Navbars

Lists

Aligning items

Mental model:

One direction (row or column)

<div class="flex items-center justify-between">


Key classes:

flex

flex-col

justify-*

items-*

gap-*

3️⃣ Grid (dashboards)

Use for:

Dashboards

Cards

Complex layouts

<div class="grid grid-cols-3 gap-4">


Mental model:

Rows + columns like a spreadsheet

Tailwind philosophy

Instead of:

.card { padding: 16px; }


You write:

<div class="p-4 rounded shadow">


Why it works:

No context switching

No naming hell

Styles stay near markup
